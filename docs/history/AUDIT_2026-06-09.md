# Audit Report — MagicQuant

**Identity:** Evolutionary hybrid GGUF quantization framework (per-tensor-group mixed-precision via evolutionary search, two-pass streaming GGUF writer, real-perplexity feedback loop). **Ownership:** user-owned (github.com/lucasmcoleman/MagicQuant). **Health grade: B** — structurally sound with a clean, byte-exact encoder boundary and an active maintenance history, held back from a higher grade by one confirmed correctness bug at the heart of its headline MoE feature plus pervasive documentation drift introduced by a recent refactor.

---

## Executive Summary

MagicQuant is a well-architected ~5,900-LOC personal tool whose core data-flow design is genuinely clean. The defining event in its recent history is the May 2026 ctypes refactor (PR0 scheme registry + PR1 libggml binding, HEAD `0fde7f0`): all quantized encoding now delegates to llama.cpp's own `ggml_quantize_chunk` via `magicquant/quant/ggml_binding.py`, making MagicQuant's quantized output **byte-identical to llama-quantize by construction** (verified by 9 passing encoder-parity tests) and deleting ~850 lines of hand-rolled numpy K-quant encoders. That refactor silently fixed every CRITICAL/HIGH finding in the project's own April audit docs — which are now stale and actively misleading.

The single most important thing to fix is a **confirmed correctness bug**: MoE up/gate expert tensors (`ffn_up_exps`, `ffn_gate_exps`) misclassify into the dense-FFN group **U** instead of the experts group **X** (empirically reproduced). Since experts are the bulk of MoE parameters and aggressive MXFP4 compression of experts is the project's entire premise, two-thirds of expert weights silently escape the intended scheme. This is compounded by two structural gaps that all point the same direction: the evolutionary search ignores the X/R/S groups entirely, and the predictor never receives per-group parameter counts — so the exact MoE/SSM models the tool was built to optimize are the ones it models and searches incorrectly. Overall health is good; none of the findings are remotely exploitable, and the architecture is in shape to absorb every fix.

---

## What's Right

- **Quantization correctness is provable, not asserted.** `converters.py:encode_to_ggml_bytes` is the sole encoder entry point and dispatches all quantized formats to the real libggml via ctypes (`ggml_binding.py`). `tests/integration/test_encoder_parity.py` byte-compares the output against `llama-quantize` for 9 schemes — all pass. This is a much stronger guarantee than the old numpy reimplementation and eliminates an entire class of K-quant encoding bugs.
- **Defensive runtime checks in the binding.** `ggml_binding._verify_type_ids()` cross-checks every `(name, type_id)` against what the loaded libggml reports at startup, failing loudly on ggml-version drift; `encode()` asserts the written byte count equals the expected size; non-floating input is rejected at both the writer worker and `encode_to_ggml_bytes`.
- **Documented invariants actually hold in code.** MXFP4 = ggml type 39 is consistent across `writer.py:69`, `ggml_binding.py:54`, `reader.py:75`, `schemes.py`, and `source.py`; BF16 uses correct round-to-nearest-even (`converters.py:62-68`); source-must-be-float is enforced with clear errors.
- **The two-pass streaming writer is a sound design for the scale.** Pass 1 computes offsets without touching data; Pass 2 overlaps read+encode (background thread, bounded `maxsize=2` queue) with disk writes, validates running file position against the precomputed aligned offset, and falls back to F32 when a row isn't block-aligned.
- **`schemes.py` is a genuine single source of truth.** A frozen dataclass carries bpw/noise/neighbors derived from real ggml block byte sizes; predictor, survival, probing, naming, and writer all read attributes off it rather than holding parallel dicts. Adding a scheme is mostly a registry append.
- **The team acted on prior review.** Every top CRITICAL/HIGH item from the in-repo April audits is fixed at HEAD: additive collapse penalty (`predictor.py:79-84`), unified tier classification via `_classify_tier`, corrected `size_score = 1 - predicted/baseline`, dtype guards, subprocess timeouts/retries (tenacity), param-count-based baseline sizing.
- **Solid operational ergonomics.** Lazy `LlamaCppTools` so prediction-only mode runs without llama.cpp; a `--dry-run` validator; structlog with a consistent stage/event schema in the orchestrator; an unusually complete HF→GGUF name/config mapping covering MoE, Granite hybrid Mamba, and Qwen3.5 linear-attention/MRoPE.
- **A real, well-chosen test suite.** Dtype-guard rejection tests, per-scheme output-size parametrization, BF16 round-trip, encoder byte-parity, and a seeded refactor-regression fixture that pins evolutionary-search behavior across refactors.
- **A well-specified roadmap.** A complete design spec plus four phased, agent-executable PR plans with verification commands and acceptance criteria — PR2/PR3/PR4 are largely "just execution."

## What's Wrong

### Critical
None. (The CRITICAL items in the in-repo April audit docs are all fixed at HEAD; see the doc-drift findings below.)

### High

- **MoE up/gate expert tensors misclassify as dense FFN (U) instead of experts (X).** — `magicquant/gguf/tensor_groups.py:40` — *Empirically confirmed:* `ffn_up_exps.weight → U`, `ffn_gate_exps.weight → U`, `ffn_down_exps.weight → X`. The X regex list contains `r'ffn.*expert'` (requires the literal word "expert", but GGUF uses the `_exps` suffix) plus explicit `ffn_gate_up_exps` and `ffn_down_exps` — but **not** `ffn_up_exps` or `ffn_gate_exps`. Because the patterns dict is iterated with X before U and X misses these, they fall through to U (`r'ffn_up'`, `r'ffn_gate(?!_inp)'`). For Mixtral/Qwen-MoE/DeepSeek-MoE, two-thirds of expert weights (up + gate) get the U group's scheme; a user setting `{X: MXFP4_MOE, U: Q6_K}` to compress experts instead gets Q6_K on the majority of expert params. This breaks the core size/quality tradeoff and skews sensitivity probing and search for exactly the models CLAUDE.md names as the primary value case. **Fix:** add `r'ffn_(up|gate|down)_exps'` (or `r'_exps'`) to the X list; add a regression test asserting all three of `ffn_{up,gate,down}_exps` → X.

- **Evolutionary search silently ignores MoE expert (X), router (R), and SSM (S) groups.** — `magicquant/orchestrator.py:198,505`; `magicquant/evolution/survival.py:46,95-101` — *Confirmed:* the orchestrator probes and weights X/R/S when present, but calls `survivor.run_evolution(verbose=verbose)` **without** `groups`, so it falls back to `DEFAULT_GROUPS = ['E','H','Q','K','O','U','D']`. The population, mutation, and tournament logic never vary X/R/S — those tensors only ever receive the base quant. For MoE models where experts are ~80-90% of params, the largest parameter block is excluded from optimization entirely. This is a leaky abstraction: the prober knows about S/X/R, the search does not. **Fix:** thread the detected group list into `run_evolution(groups=...)`; add a test that an expert-bearing model produces configs that vary the X scheme.

- **CLAUDE.md (the maintainer/agent contract) describes deleted code and a fictitious quality gap.** — `CLAUDE.md:19,44-46,67` — CLAUDE.md still states "Encoders are vectorized with numpy… K-quant encoders use RMSE-optimized scale selection… Quality gap is ~10-27% MSE vs llama.cpp native" and "No test suite exists yet." Commit `04bb0b1` deleted ~850 lines of numpy quantizers; `converters.py` is now 126 lines dispatching to libggml, output is byte-identical (the MSE gap is **0**, verified by parity tests), and a 28-test suite exists. CLAUDE.md is the document Claude Code and future maintainers treat as ground truth; it currently describes an architecture deleted a month ago. **Fix:** rewrite the converters/Known-Limitations sections to describe `ggml_binding.py`, the type-ID drift check, and byte-parity; remove the MSE-gap and "no test suite" claims.

- **Roadmap stalled at PR1: Q2/Q3 tier bands still cannot produce output.** — `magicquant/quant/schemes.py:184-203`; `docs/superpowers/specs/2026-05-04-magicquant-encoder-expansion-design.md` — PR0/PR1 merged (Q2_K/Q3_K registered), but PR2 (legacy Q-quants), PR3 (IQ-quants), and PR4 (imatrix) are not. The registry holds only 9 schemes; lowest is Q2_K at 2.625 bpw; the robust floor is still Q4_K_M. Per the spec, the Q2 band (ratio ≤ 0.16) needs sub-Q2_K IQ-quants from PR3 to fill — but `orchestrator._classify_tier` and CLI defaults can request a Q2/Q3 tier no scheme can satisfy, so `generate_tiered_models` silently logs "No config for tier, skipping." The ctypes binding already lists IQ1_S..IQ4_XS, so this is purely registry-level work. **Fix:** execute PR3 (register the IQ-quants + lower the robust floor) — the single change that makes the headline deliverable real.

### Medium

- **Predictor never receives per-group `parameter_counts`; MoE size/speed predictions use a hardcoded dense distribution.** — `magicquant/orchestrator.py:171,491`; `magicquant/evolution/predictor.py:144-153` — *Confirmed:* both `PredictiveScorer` constructions pass `sensitivity_weights/baseline_size_gb/baseline_tps` but not `parameter_counts`, so `_compute_param_dist` always hits the `_DEFAULT` dense table `{'E':.04,'H':.04,'Q':.12,'K':.12,'O':.06,'U':.31,'D':.31}` with no X/R/S entries (those get the 0.05 default). The actual-count branch added to "fix" LOGIC_AUDIT #13 is dead in the real pipeline. For an MoE where experts are ~85% of params, `predict_size`/`predict_tps` effectively ignore the bulk of the model, mis-calibrating tier classification and `size_score`. The measured loop partially corrects loss via residuals, but **size prediction is not residual-corrected**, and prediction-only mode (`--rounds 0`) relies entirely on the wrong distribution. **Fix:** accumulate per-group element counts in `_estimate_model_size` (it already iterates `get_all_tensors_info()`) and pass them to `PredictiveScorer`.

- **`noise_factor` values are uncalibrated placeholders; the calibration bench was never run.** — `magicquant/quant/schemes.py:156-181`; `tools/calibrate_noise_factors.py` — *Confirmed:* `tools/calibration_results.json` does not exist. Q3_K (`noise_factor=8.0`) and Q2_K (`15.0`) carry literal `# placeholder` comments; the module docstring still says PR1 will replace them. The predictor's loss prediction and the random-config sampler both weight schemes by these guessed constants, so initial population bias and prediction-only search rest on unvalidated values (worst for the two new schemes). **Fix:** run `python tools/calibrate_noise_factors.py`, commit `calibration_results.json`, paste measured values into `schemes.py`. ~1.5-2 hr compute, zero coding; closes PR1's last two acceptance items.

- **Worker-thread exception leaves a partial/loadable GGUF on disk.** — `magicquant/gguf/writer.py:498-556` — *Confirmed:* the enclosing `finally` (line 555) only calls `source.close()`; there is no `unlink`/`os.replace`. If `_read_encode_worker` raises (dtype guard, shape mismatch, encoder size error, OOM), the main loop re-raises but the partially-written `.gguf` — with a valid-looking header and some tensor blobs — remains. llama.cpp may load it and produce garbage, or a later run may mistake it for a completed model. (This is the still-open April finding H-5.) **Fix:** build to `output_path + '.partial'` and `os.replace()` only after `worker.join()` succeeds.

- **`imatrix` plumbed into the encoder leaf but never threaded through the writer.** — `magicquant/gguf/writer.py:212`; `magicquant/quant/converters.py:81-126` — `encode_to_ggml_bytes` and `ggml_encode` accept `imatrix` and pass it to `ggml_quantize_chunk`, but the writer worker calls `encode_to_ggml_bytes(f32, target)` with no imatrix, and nothing captures one (no `magicquant/imatrix.py`; PR4 unstarted). All K-quant/IQ encoding runs unweighted — for imatrix-requiring IQ1/IQ2 this is the difference between usable output and gibberish (PR3's own parity tests mark those xfail pending PR4). **Fix:** implement PR4 — capture activation magnitudes (subprocess `llama-imatrix` initially), thread `Optional[np.ndarray]` through `create_hybrid_gguf → _read_encode_worker → encode_to_ggml_bytes`, gated on `ggml_quantize_requires_imatrix()`.

- **Two parallel configuration systems; env-var config only reaches `--dry-run`.** — `magicquant/config.py`; `magicquant/__main__.py:130-166,293-309`; `README.md:156-169` — The pydantic `MagicQuantSettings` (env-prefixed `MAGICQUANT_`, `.env`, `validate_paths()`) is instantiated **only** in `cmd_dry_run`. `cmd_search/cmd_generate/cmd_hybrid` read argparse directly, so `MAGICQUANT_*` env vars and `validate_paths()` apply to dry-run only, despite the README advertising env-var config for all runs. Defaults also diverge (config.py 30/80 vs argparse 50/100). `python-dotenv` is a declared dependency but never imported. **Fix:** either route real commands through `MagicQuantSettings` (argparse overrides settings) or scope the README down to dry-run and drop `python-dotenv`; reconcile the defaults.

- **Two Dockerfiles, both likely broken by the mandatory `llama-cpp-python` dependency.** — `Dockerfile:7-29`; `docker/Dockerfile:32-34` — Root Dockerfile (`python:3.12-slim`) installs the wheel with no compiler toolchain; `llama-cpp-python` (now a hard dep, `pyproject.toml:21`) compiles from sdist when no manylinux wheel matches, and slim has no gcc/cmake. `docker/Dockerfile` builds llama.cpp in a builder stage but runs `pip3 install -e .` in a runtime stage without `build-essential`. Both documented container paths (README, Makefile, compose) break. **Fix:** add `build-essential`+`cmake` to the runtime layer or pin a prebuilt wheel; consolidate to one Dockerfile.

- **`requirements.txt` is stale and install-breaking.** — `requirements.txt:1-2` — *Confirmed:* lists only `numpy` and `pyyaml`; the real deps in `pyproject.toml` are numpy, pydantic-settings, structlog, tenacity, python-dotenv, llama-cpp-python (pyyaml is an optional extra). `pip install -r requirements.txt` yields an environment that can't import `magicquant.logging` (no structlog) and can't bind libggml. **Fix:** delete it (pyproject is the source of truth) or regenerate from pyproject.

- **Pre-quantized / UNKNOWN source handling is a leaky special case in the writer hot path.** — `magicquant/gguf/writer.py:364-368,389-408`; `magicquant/gguf/source.py:118-131` — The `ModelSource` contract promises `read_tensor_f32` returns float32, but the writer must special-case undecodable sources via `can_decode` + a second validation pass. `GGUFSource.get_source_type_name` returns the literal `'UNKNOWN'`, which flows into `GGML_TYPE.get(source_type_name, 0)` → silently maps UNKNOWN to ggml type 0 (F32) while `read_tensor_f32` returns None, producing a **zero-filled blob**. An UNKNOWN tensor whose group already maps to the source type slips past the `bad_tensors` check. **Fix:** make the contract explicit (`can_quantize()`/dtype property; have `read_tensor_f32` raise), treat UNKNOWN as a hard error in Pass 1, consolidate the validation.

- **No HuggingFace publishing path despite the project being framed around publishing hybrid quants.** — `README.md:9-14`; `magicquant/` (absent) — The README centers on producing models for HF collections, but there is no model-card generation, no upload helper, and no provenance stamping beyond the `magicquant.hybrid/base_quant/group_schemes` metadata keys. `search_results.json` (per-tier measured PPL/size) is not turned into a card, so provenance is lost on upload. **Fix:** add a `magicquant publish`/`card` command that reads `search_results.json` + the GGUF and emits a model card (tier table, measured PPL/loss, scheme map, attribution); optionally call `huggingface_hub.upload_file`. High value-to-effort — the data already exists.

## What Needs Improvement (themes, not single bugs)

- **The MoE/SSM story is half-wired across the pipeline.** Three independent findings — the X-pattern classification gap (High), the search ignoring X/R/S (High), and the predictor's dense-only param distribution (Medium) — all converge on the same conclusion: the classifier, prober, and registry model X/R/S, but the search and predictor don't consume them. For a tool whose stated value "comes from MoE models with larger search spaces," closing this trio is the highest-leverage architectural work. They should be fixed together and covered by one MoE end-to-end test.
- **Documentation drift is the dominant non-code liability.** The May refactor was real and good, but nothing downstream of the code was updated: CLAUDE.md (the agent/maintainer contract), both in-repo audit reports, README env-var/BF16 claims, `requirements.txt`, the version string, and both Dockerfiles. Individually minor; collectively they make the repo describe a system that no longer exists and break the documented install/container paths. A single "sync docs to HEAD" pass clears most of it.
- **Configuration and output discipline are split-brained.** Two config systems (pydantic vs argparse) with diverging defaults where only argparse is honored; structlog in some modules and bare `print()` in the pipeline-critical `probing.py`/`llamacpp.py` paths (so `verbose=False` still leaks output). Neither is an emergency for a LAN tool, but both undercut reproducibility and observability.
- **No CI, no linter, no lockfile.** The Makefile has test/lint targets but nothing runs them; `format` literally prints "No formatter configured." The encoder-parity tests guard the core invariant and should run on every commit (with a skip-with-warning when `llama-quantize` is absent). Dependencies are lower-bound only — risky for a tool that ctypes-binds into `llama-cpp-python`'s bundled libggml (mitigated only by the runtime `_verify_type_ids` check).
- **Test coverage has a shaped hole.** The encoder is well-covered in isolation, but there is no end-to-end `create_hybrid_gguf` smoke test (read → classify → write → reopen with GGUFReader → assert offsets/types), no SafetensorsSource/LoRA fixtures, and — most consequentially — no table-driven tensor-group classification test (which would have caught the MoE bug immediately).

## Missing Features & Roadmap (prioritized by value-to-effort)

The project has a clear 5-PR roadmap (`docs/superpowers/specs/2026-05-04-magicquant-encoder-expansion-design.md` + PR0–PR4 plans). PR0/PR1 merged; PR2/PR3/PR4 are written but unexecuted.

1. **PR3 — register the IQ-quants + lower the robust floor.** (~400 lines registry + tests.) The single change that lets the Q2/Q3 tier bands produce output — the headline deliverable. Binding support already exists (`GGML_TYPE_IDS` lists IQ1_S..IQ4_XS). **Highest value-to-effort.**
2. **Run the calibration bench + commit `calibration_results.json`.** Closes PR1's last two acceptance items; ~1.5-2 hr compute, zero coding. Replaces guessed `noise_factor` placeholders that drive loss prediction and scheme sampling.
3. **Per-group `parameter_counts` into the predictor.** Small change (`_estimate_model_size` already has the data); makes MoE/SSM size/tier predictions correct.
4. **Thread X/R/S into the search + add S/X/R sensitivity heuristics.** Realizes the project's stated primary value (MoE optimization).
5. **PR4 — imatrix capture and threading (`magicquant/imatrix.py`).** Required for usable IQ1/IQ2 quality and to close the residual quality gap on K-quants; needed before PR3's IQ parity tests can flip from xfail.
