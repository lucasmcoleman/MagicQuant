# MagicQuant Audit — 2026-07-01

**Scope:** Full-codebase correctness / quality-ops / security / architecture audit of MagicQuant, the evolutionary per-tensor-group hybrid-GGUF quantization toolkit (search → measure → pack via libggml, plus QAT-LoRA and the opt-in ROCmFPX/IQ scheme families).
**Method:** Adversarial multi-angle verification of candidate findings against the current tree; every reported finding was re-checked at `file:line` on HEAD.
**Git state at audit time:** HEAD = `feature/mq-hardware-items` @ `ab1d80c`, 2 commits ahead of `origin/master`. `master`, `feature/qat`, `feature/rocmfpx-schemes`, and `origin/master` all point to `8465340` — the June pack-bug fixes, QAT-LoRA, imatrix (M4), block-32 fallback, and the ROCmFPX/IQ opt-in schemes are all merged **and** pushed. (A candidate finding claiming this work was stranded on an unmerged/unpushed branch was verified false and is **retracted** — see the appendix.)

---

## Health grade: **B**

A genuinely well-engineered single-user research tool: broad, green test suite (227 passed / 6 skipped core; 243 passed / 1 skipped under the QAT venv), a crash-safe GGUF writer, careful defense-in-depth gating on the new fork schemes, and all four documented June pack-bug fixes present and correct. No high-severity crash/corruption/security defect survived verification. What holds it back from an A-band grade: a cluster of *silent* medium-severity correctness/ops defects (a sampler that violates its own documented weights, a calibration loader whose schema doesn't match the file it loads, a multi-hour search that can report success with zero results), the single most expensive operation in the tool running CPU-only on a ROCm box, and a coverage hole — the top-level orchestrator has **zero** unit tests, and a substantial new KL/imatrix/speed-bench feature surface has just landed on the working branch unaudited and untested.

---

## Executive summary

MagicQuant does its hardest job well: byte-exact GGUF packing through libggml, crash-safe atomic writes, hard-fail on unknown tensors, and correct RoPE/bias/pre-tokenizer handling for HF→GGUF conversion. The defects that survived adversarial verification are not in the packing core — they are in the **search heuristics and operational plumbing** around it, and they share a theme: they fail *silently*. The random-config sampler ignores its own documented per-category weight tables (MXFP4, the tool's headline FFN scheme, ends up the *least*-sampled category at ~15% vs a documented 33%). The calibration loader reads a flat dict while the calibration tool writes a nested one, so a completed ~2-hour calibration run is a no-op with no error. A measured search where every candidate build fails still writes a results file and exits 0. None of these throw, warn, or fail a test. Separately, the biggest *opportunity* is operational: the llama.cpp perplexity/quantize subprocesses that dominate search wall-clock time are invoked with no `-ngl`/GPU flags, so the most-repeated operation in the tool runs CPU-only on this AMD ROCm box. Fixing the sampler, the calibration schema, and adding GPU offload are all small, high-leverage changes.

## What's good

Concrete, verified strengths worth preserving:

- **Byte-exact, crash-safe GGUF writing.** `writer.py:650-666` writes to a sibling `.partial` file and only `os.replace()`s it into place after a fully successful write; an `except BaseException` handler unlinks the temp file on any failure (including worker-thread exceptions), and a hung encoder thread is detected and aborted rather than shipping a truncated file. No corrupt output can be left at the final path.
- **All four June pack-bug fixes are present and correct** in the current tree, each with a docstring naming the failure mode it prevents: bias name-mapping (`c9be108`), transformers≥5 merges/nested-rope handling (`558eeb3`), `tokenizer.ggml.pre` detection (`271ba5f`), and llama-family Q/K rope permutation (`094d409`). LoRA-merge-on-read correctly re-applies the same rope permutation to the LoRA delta before merging, with a loud shape-mismatch guard.
- **The new ROCmFPX/IQ opt-ins are defense-in-depth gated.** Zero sampling mass when disabled *and* an explicit filter drops the schemes from the candidate pool; the ctypes binding probes fork-type support **by name** (`ggml_type_from_name`) so an out-of-range enum id is never indexed into a stock libggml's `type_traits` array; `_verify_type_ids` skips unsupported fork ids; imatrix-required schemes are excluded from both random sampling and (as of `8465340`) neighbor-walk mutation, so the writer's Pass-1 imatrix hard-error is unreachable from the search.
- **Solid llama.cpp subprocess hygiene** in `utils/llamacpp.py`: explicit per-call timeouts (600s/1800s), tenacity retry with exponential backoff on transient `CalledProcessError` (GPU OOM/file lock), and a stderr+stdout scan for the perplexity line (fixing a documented prior miss).
- **Rich structured logging** (`structlog`) in `orchestrator.py`/`writer.py` with query-friendly fields (`stage=`, `progress=`, `tensor=`, `exc_info=`); per-candidate build failures are caught and logged without sinking the whole multi-hour run (`orchestrator.py` `_build_candidate` try/except).
- **A real, green regression suite:** crash-safety (`.partial` + `os.replace`), UNKNOWN-tensor hard-error, MoE `*_exps` classification, a seed-pinned refactor-regression fixture, the sensitive-group floor clamp, and a well-isolated fork-gated live-encode round trip for ROCmFPX.
- **Defensive calibration loader contract:** a missing/malformed/unreadable calibration file degrades to an empty dict rather than raising (unit-tested) — the problem in Finding 2 is a *schema* mismatch, not a robustness gap.

#### F1 — Random-config sampler never normalizes per-category weight; documented FFN class shares are silently violated
**Severity: Medium** · correctness · verified 3/3 angles
**Location:** `magicquant/evolution/survival.py:388-403` (`_generate_random_config`); class-weight tables at `:302-322`

`_FFN/_ATTENTION/_BRAIN_CLASS_WEIGHTS` each sum to 1.0 and are documented (`:291-294`) as *"the relative probability mass for picking ANY scheme in that category."* But the sampler builds one weight per scheme as `cat_weight * (1/(1+noise_factor))` (`:394`) with **no division by the number of schemes sharing a category**, then hands the raw list to `random.choices`, which normalizes globally. The code's own comment at `:393` — *"Normalize within a category later"* — describes a normalization that never happens.

Effect: a category's realized sampling mass scales with its *member count*, not its documented weight. Reproduced against the live registry: with `enable_iq=False`, the FFN `k_quant` category (5 schemes) gets **61.3%** of mass vs a documented 30%, while `mxfp4` (1 scheme) gets **14.7%** vs a documented 33% — the highest-documented category becomes the least-sampled. With `enable_iq=True` it worsens: `mxfp4` → 10.6%, `iq_quant` → 38.0%. No test checks per-category shares.

**Impact:** Every default `magicquant search` (and Foundry's MagicQuant stage) skews random-fill and epsilon-greedy exploration ~4× toward legacy k-quant and away from MXFP4 relative to design intent — reducing exploration of the intended MXFP4-heavy region. Not fatal (hand-written MXFP4 seeds still enter the population and the measured feedback loop applies corrective pressure), which is why this is medium, not high — but it silently violates a documented invariant that encodes the tool's headline value proposition.

**Fix:** Within each category, divide each scheme's inverse-noise weight by the sum of inverse-noise weights of schemes in that same category before multiplying by `cat_weight` (i.e. actually implement the `:393` comment). Add a test asserting empirical per-category sampling mass matches `_FFN/_ATTENTION/_BRAIN_CLASS_WEIGHTS` within tolerance.

#### F2 — Calibration loader expects a flat dict; the calibration tool always writes a nested `"schemes"` object — calibrated noise factors are silently never used
**Severity: Medium** · correctness · verified 3/3 angles (2 medium, 1 high)
**Location:** `magicquant/quant/calibration.py:65-66` (`calibrated_noise_factor` / `_load`) vs `tools/calibrate_noise_factors.py:204-211` (output shape)

The tool writes `out = {"model":…, "corpus":…, "date":…, "baseline_ppl":…, "schemes": results}` — per-scheme stats live under `out["schemes"][name]` — to its default `--output` `tools/calibration_results.json`, which is exactly the file the loader reads (`calibration.py:23`). But the loader does `data = _load(); entry = data.get(scheme_name)` against the **top-level** parsed JSON (whose only keys are model/corpus/date/baseline_ppl/schemes). It never unwraps `"schemes"`, so `data.get("Q8_0")` is always `None` and `calibrated_noise_factor()` returns `None` for every scheme in a real calibration file. Both callers — `predictor.py:224-228` and `probing.py:295-299` — treat `None` as "fall back to the static `schemes.py` registry value," with no error or warning.

The test suite masks it: `tests/test_calibration_loader.py` fixtures write the **flat** shape `{"Q8_0": {...}}` the loader expects, never the nested shape the tool emits, so the suite stays green.

**Impact:** A user who follows the documented workflow and runs `python tools/calibrate_noise_factors.py` (a ~2-hour compute job) produces a valid file that is then **silently ignored** — every subsequent search/predict/probe keeps using the uncalibrated heuristic noise factors, exactly as if calibration were never run. Currently latent (no `calibration_results.json` exists yet), which caps the blast radius, but it defeats an entire documented feature the moment someone uses it.

**Fix:** Change the loader to read `data.get("schemes", data).get(scheme_name)` (tolerating both shapes), *or* change the tool to write a flat top-level dict. Add a round-trip test that feeds the **actual** `tools/calibrate_noise_factors.py` output shape through `calibrated_noise_factor`, not a hand-written flat fixture. Note `probing.py:295-299` is a second silent victim of the same bug.

#### F3 — Measured search can silently "succeed" with zero results; no empty-result guard, and `orchestrator.py` has no unit tests
**Severity: Medium** · quality-ops · verified 3/3 angles (2 medium, 1 low)
**Location:** `magicquant/orchestrator.py:279-365` (measurement loop), `:435-448` (`_select_final_survivors`), `:490-497` (`_save_results`); `magicquant/__main__.py:197-198` (`cmd_search`)

The baseline-PPL failure *is* guarded loudly (`orchestrator.py:174-185` raises `RuntimeError`), so a "bad llama.cpp build" fails fast. The residual gap is narrower but real: **baseline succeeds, then every candidate build/measure fails** (disk full mid-run during multi-GB GGUF writes, a config/arch-specific `create_hybrid_gguf` bug swallowed by `_build_candidate`'s except at `:431-433`, OOM on every hybrid pack). In that case `self._measured` stays `{}`, `_select_final_survivors` returns `{}`, `_save_results` writes a `search_results.json` with empty measurements/tiered, and `cmd_search` unconditionally prints "Results saved to: …" and exits 0. Downstream `generate_tiered_models` logs "No config for tier, skipping" — indistinguishable from the documented, expected Q2-unreachable case — so a fully-failed run reads as a normal partial one. It is not perfectly silent (per-candidate ERROR "Build failed" is logged when verbose), but the exit code, final message, and results file all signal success.

Underlying this: `orchestrator.py` (879 lines, the top-level Predict→Measure→Learn coordinator) has **zero** direct unit tests. `run_measured_search`, `run_full_search`, `_save_results`, `_select_measurement_candidates`, `_select_final_survivors`, `_build_candidate`, and the generate* methods are exercised nowhere; `test_config_routing.py` replaces the orchestrator with a fake.

**Impact:** A systemic failure during the tool's own stated unattended/overnight workflow reports success and silently discards hours of compute, and there is no test protecting the core coordination logic from regressions.

**Fix:** When `measurement_rounds > 0` and `self._measured` is empty after all rounds, raise (or emit a distinct ERROR + non-zero exit). Add `tests/test_orchestrator.py` covering `_save_results` / `_select_final_survivors` / `_build_candidate` with mocked `LlamaCppTools` + writer, including an all-measurements-fail scenario.

#### F4 — No checkpoint/resume for the measured search loop; a crash forfeits all probing + measurement work, and the final write is non-atomic
**Severity: Medium** · quality-ops · verified 3/3 angles
**Location:** `magicquant/orchestrator.py:241-368` (rounds loop), `:496-497` (single non-atomic `_save_results` write)

`run_measured_search` accumulates every measurement into the in-memory `self._measured` (initialized empty in `__init__`, never rehydrated from disk) and persists it exactly **once**, via a plain `results_path.write_text(json.dumps(...))` at `:497`, after **all** `measurement_rounds` complete. Each round builds and llama-perplexity-measures full GGUFs (expensive, GPU/CPU-bound) and unlinks each candidate after measuring, so nothing survives on disk mid-run. A kill/OOM/Ctrl-C at any point before `:368` — including partway through the last round of a long overnight run — loses all measurement (and forces re-probing) with no resume. The final write is also **not** the crash-safe `.partial` + `os.replace` pattern the codebase already uses for GGUF output (`writer.py:651-666`), so a kill mid-write can truncate `search_results.json` (which downstream `qat/config.py` and Foundry then fail to parse).

**Impact:** For the documented unattended-GPU workflow, any interruption near the end of a run forfeits the entire run's compute (recoverable only by full rerun) rather than just the in-flight candidate. Medium, not high: normal completion is correct, lost work is recomputable, the corruption window is small.

**Fix:** Persist `self._measured` (and round index) incrementally after each measurement round using the same atomic `.partial` + `os.replace` pattern; on startup, detect a prior partial checkpoint and offer/`--resume` to reload it, skipping already-measured `config_key`s (the skip machinery at `:284-291` already supports a non-empty starting dict). Warm-resume also unblocks the per-arch residual-cache reuse in *What's missing* below.

#### F5 — QAT-LoRA training hard-disables checkpointing (`save_strategy="no"`); an interrupted run loses 100% of progress, undocumented
**Severity: Low** · quality-ops · verified 2/3 angles confirm (1 refuted as intentional)
**Location:** `magicquant/qat/train.py:471` (`TrainingArguments`, `save_strategy="no"`)

`run_qat` hard-codes `save_strategy="no"`, so the HF Trainer never writes an intermediate checkpoint; the adapter is persisted only at `:488` (`_save_adapters`), strictly after `trainer.train()` returns. There is no `resume_from_checkpoint`, no `save_steps`, and no save callback anywhere in `qat/` (only *gradient* checkpointing, an unrelated concept). `epochs`/`max_steps` are user-configurable. An interruption before completion discards the entire session with no partial adapter and no resume.

**Verifier disagreement, honestly noted:** one angle **refuted** this as not-a-bug: `save_strategy="no"` is an explicit, deliberate choice in a clean minimal `TrainingArguments` block, the persistence path (end-of-run `_save_adapters` + `qat_meta.json`) is by design, and the "high severity" framing rested on an unsupported "meant to run overnight" premise — the documented/validated QAT usage is a *short* LoRA-only recovery run (0.5B base, `--epochs 1`, batch size 1, minutes). The two confirming angles agree it is real but downgrade to low: correct output when it completes, fully restartable from the persisted dataset + config, cost is recompute time not data loss. Reported as **low** on that basis.

**Fix (optional / low priority):** If longer QAT runs become a real workflow, add `save_strategy="steps"` checkpointing to a subdir of `out_dir` and wire `resume_from_checkpoint` into `run_qat`/`cmd_qat`; otherwise document the current non-resumability in "Known Limitations."

### Minor findings (unverified — flagged from a single pass, not adversarially confirmed)

Label: **these were not put through the multi-angle verifier.** Treat as leads.

- **M1 [Medium · correctness] Block-32 K-quant fallback misclassifies the new sub-4-bit IQ schemes.** `writer.py:247` hard-codes `low_bit = target_ggml_name in ("Q2_K","Q3_K","Q4_K","IQ4_NL","MXFP4")` — never extended when the IQ family (`IQ4_XS/IQ3_S/IQ3_XXS/IQ2_S/IQ2_XS/IQ2_XXS/IQ1_M/IQ1_S`, all 1.56–4.25 bpw) was registered. With `enable_iq=True`, a low-bit IQ target on a non-256-divisible row width falls back to `Q8_0` (8.5 bpw) instead of `MXFP4` (4.25 bpw) — a ~2.8× larger-than-intended blob, the exact size blow-up the fallback exists to prevent. **Fix:** derive `low_bit` from the registry's `bits_per_weight` (e.g. `< 4.5`) instead of a hand-maintained tuple; extend `tests/test_writer_block_fallback.py` to cover an IQ member.

- **M2 [Medium · security] Path traversal via unsanitized `model.safetensors.index.json` `weight_map`.** `source.py:827` does `full = os.path.join(self._model_dir, filename)` on untrusted `weight_map` values with no containment check, then mmaps `full` as tensor data. An absolute or `../../` filename escapes the model dir (`os.path.join('/safe', '/etc/passwd') == '/etc/passwd'`). Notably the sibling LoRA path (`source.py:1255-1266`) explicitly hardens against this exact class — the discipline just wasn't applied here. **Fix:** `full = os.path.realpath(os.path.join(self._model_dir, filename))` and raise unless `os.path.commonpath([full, realpath(model_dir)]) == realpath(model_dir)`. (Real-world severity is bounded on a single-user box, but this is the primary intended workflow: quantizing third-party model dirs.)

- **M3 [Low · security] LoRA `base_model_name_or_path` relative-path resolution lacks a containment check** (`source.py:1261-1266`). Absolute paths / HF repo-ids / URLs are already correctly rejected, but a relative `../../other-dir` that resolves to an existing dir is accepted, allowing a malicious adapter to silently substitute a different local base model. **Fix:** apply the same `commonpath` containment check as M2.

- **M4 [Medium · architecture] The ggml type-id→name table is hand-duplicated in three places, only one runtime-verified.** `ggml_binding.py:29-69` self-verifies via `_verify_type_ids`; `writer.py:39-76` (`GGML_TYPE`) and per-scheme `ggml_type_id` in `schemes.py` re-declare the same ids with no drift guard. `converters.py:27-33` documents that a prior hand-duplicated block-size table already caused a corrupt-offset bug (IQ4_XS 32/18 vs 256/136) and was consolidated — the id table wasn't. **Fix:** derive `writer.py`'s `GGML_TYPE` (and ideally `schemes.py`'s ids) from `ggml_binding.GGML_TYPE_IDS`, as `converters.py` already does for block/type sizes.

- **M5 [Medium · architecture] Search-group detection + predictor init are copy-pasted** between `run_measured_search` (`orchestrator.py:199-236`) and `run_full_search` (`:563-592`) — ~38 near-identical lines. This is precisely the area (group detection / model introspection) where the historical pack bugs and the June MoE X/R fix lived; a future fix or a new group risks landing in only one path. **Fix:** extract `_detect_search_groups()` / `_init_predictor()` shared helpers.

- **M6 [Medium · architecture] `enable_rocmfpx` / `enable_iq` are Python-API-only** — no `MagicQuantSettings` field, no CLI flag (`__main__.py`/`config.py`), so `magicquant search` users can never opt into ROCmFPX or the IQ schemes. CLAUDE.md phrasing implies CLI parity. *Caveat: CLAUDE.md is partly stale (see open questions), so verify intent before acting.* **Fix:** add `--rocmfpx`/`--iq` flags + settings fields, or tighten the docs to say CLI access exists only via Foundry.

- **M7 [Low · architecture] `Q4_0_ROCMFP4_FAST` (id 101) is wired into the encoder/writer/binding tables but no `QuantizationScheme` registers it** (`schemes.py` omits it from `_REGISTRY`/`ROCMFPX_SCHEME_NAMES`) — inert dead capability that looks wired-up. **Fix:** register it or remove it with a "reserved" comment.

- **M8 [Low · architecture] `PredictiveScorer` duplicates its weighted-average math** between the real-`parameter_counts` path and the fallback-distribution path (`predictor.py:93-111` vs `:191-214`, `:113-137` vs `:168-189`), including the "FFN groups get 2× weight" rule embedded twice. A one-sided edit would diverge measured vs prediction-only search. **Fix:** factor one `_weighted_average(...)` helper.

- **M9 [Low · architecture] CHANGELOG.md stops at 0.2.0** (`:3`) while `pyproject.toml:7` declares 0.3.0 — none of Q3_K/Q2_K, the IQ family, imatrix, QAT-LoRA, ROCmFPX, block-32 fallback, or the June fixes are recorded. **Fix:** add a 0.3.0 entry.

- **M10 [Low · architecture] `gguf/source.py` is a 1297-line module** mixing the `ModelSource` ABC, three implementations, and ~450 lines of HF-metadata/tokenizer translation (the area that produced three of four June pack bugs). **Fix:** split HF-metadata/tokenizer functions into their own module for isolable review/testing.

- **M11 [Medium · quality-ops] No top-level exception handling in the CLI** (`__main__.py:785`, `args.func(args)` unguarded). Reproduced: `magicquant search /nonexistent/model.gguf` prints a raw multi-frame traceback ending in `RuntimeError` instead of a clean one-line error. **Fix:** wrap in try/except → structured log + actionable message; reserve tracebacks for `--debug`.

- **M12 [Medium · quality-ops] CI never installs the `[qat]` extra** (`ci.yml:16-19`, only `.[dev]`), so ~40 tests across `test_qat_*` / `test_fake_quant.py` (all `pytest.importorskip("torch")`) silently **skip** in every run — the flagship QAT feature has never been exercised by CI. **Fix:** add a matrix leg installing `.[dev,qat]` (CPU torch is fine); fail the build if the QAT suite is 100% skipped.

- **M13 [Medium · quality-ops] `configure_logging(verbose=...)` is a dead parameter** (`logging.py:13-40`) — the body never references `verbose`; `__main__.py:778` hard-codes `verbose=True` with no `--quiet`, so there is no way to reduce log noise for long runs. No `tests/test_logging.py`. **Fix:** wire `verbose` into `make_filtering_bound_logger(...)`, add `--quiet`/`-v`, add a level-filter test.

- **M14 [Medium · quality-ops] Two divergent, CI-unvalidated Dockerfiles.** The root `Dockerfile` (what README tells users to build) pip-installs the wheel but never compiles `llama-quantize`/`llama-perplexity`; `docker/Dockerfile` compiles them but has no HEALTHCHECK. Since `search` defaults `measurement_rounds=3` → `run_measured_search` → hard-requires `LlamaCppTools`, the documented quickstart fails on the root image (with M11's raw traceback). Neither is built in CI. **Fix:** consolidate/clarify, add llama.cpp CLI tools to the documented image (or default the example to `--rounds 0`), and add a CI image-build smoke test.

- **M15 [Medium · quality-ops] imatrix capture has no default timeout and no live progress** (`imatrix.py:49` `timeout=None`, `:88` `capture_output=True`). A stalled `llama-imatrix` on a large corpus blocks indefinitely with zero visible progress, unlike the rest of the toolkit's timed subprocess calls. **Fix:** sane default timeout + streamed output or an elapsed-time heartbeat.

- **M16 [Low · quality-ops] Core evolutionary loop uses raw `print()`** (`survival.py:162,176,200`; 42 `print()` calls across evolution/quant/gguf) instead of the structured logger used elsewhere; `imatrix.py` uses stdlib `logging` — a third inconsistent path. Redirecting a long run's output loses timestamps/parseability for the search phase. **Fix:** route through `magicquant.logging.get_logger`.

- **M17 [Low · quality-ops] CI lint is permanently non-blocking** (`ci.yml`: `ruff check … || true  # non-blocking until clean`). Lint can never fail CI; nothing tracks flipping it. **Fix:** ratchet the current violation count and make it blocking, or scope `|| true` to a documented allowlist.

## What's missing (capability roadmap, ordered by value ÷ effort)

1. **GPU offload for the llama.cpp measurement/quantize subprocesses — transformative value, easy.** `utils/llamacpp.py`'s `calculate_perplexity()` and `quantize_model()` build their command lines with **no** `-ngl`/`--n-gpu-layers`, `--threads`, or ROCm device flags, and `MagicQuantSettings` has no GPU/thread fields at all. This is the single most expensive, most-repeated operation in the tool (baseline + once per probed group + once per candidate per round), and on this AMD Strix Halo / ROCm box it runs 100% CPU today. Add `MAGICQUANT_LLAMACPP_NGL` / `_THREADS` settings (default: pass `--n-gpu-layers 999` when a GPU build is detected, else omit) threaded into both command lists; verify via `rocminfo` that the GPU build is actually in use. Plausibly a 5–20× wall-clock cut on overnight searches — and the same missing flag affects every Foundry caller.

2. **Fix the calibration schema mismatch and actually run calibration once — medium value, easy.** Same defect as **F2**. The wiring exists but no-ops; a one-line loader change plus a real calibration run against a model + wikitext-2 replaces the all-heuristic noise factors with measured ones — the whole point of the M6 calibration feature.

3. **Checkpoint / `--resume` for the measured search loop — high value, moderate.** Same as **F4**. Persist `self._measured` + residuals incrementally with the atomic-write pattern; reload + skip already-measured `config_key`s on resume. Turns any mid-run interruption from "lose the whole night" into "resume where it stopped."

4. **Persist the predictor residual cache, keyed per architecture, for warm starts — high value, moderate.** `PredictiveScorer.residual_cache` is populated via `record_residual` but never serialized; every run cold-starts even on a familiar arch family. Write the cache + resolved `general.architecture` to `.magicquant_history/<arch>.json` at end of run; on the next run, if the architecture matches, seed the predictor before generation 1. Reuses existing machinery — only persistence + arch-keyed lookup are new. (Aligns with the already-noted per-arch noise_factor TODO.)

5. **Multi-threaded per-tensor GGUF encode — medium value, moderate.** `writer.py`'s `_write_gguf_body` uses exactly **one** background encode worker feeding a `Queue(maxsize=2)`, even though `ggml_quantize_chunk` is a GIL-releasing C call. On a many-core APU this leaves real throughput on the table every time a hybrid is built (dozens of times per search). Replace the single worker with an N-thread pool writing results in offset order (buffer out-of-order completions), preserving the two-pass offset accounting and `.partial` crash-safety. Needs care around ordered writes and error propagation.

## Coverage gaps & open questions

Areas this audit did **not** cover in depth, ordered by how much they matter:

- **The active branch's new feature surface is entirely unaudited (biggest gap).** HEAD (`feature/mq-hardware-items`, commits `3f12a56` + `ab1d80c`, 2 ahead of `origin/master`) adds KL-divergence scoring (`save_base_logits`/`calculate_kl_divergence`, `_kl_*` state), imatrix auto-capture wiring (`enable_imatrix`/`use_imatrix`), speed-bench recording, and a new `_selection_score()` that blends `|mean_kl|` into final-survivor ranking — all bolted onto `orchestrator.py`, the exact file with **zero** unit tests (F3). No test imports these methods. Open question: does the KL path enforce identical corpus + `ctx_size` + `chunks` between the base-logits run and each candidate run? `save_base_logits`/`calculate_kl_divergence` default `chunks=-1` while the orchestrator resolves ctx/corpus separately — a silent mismatch would make the KL score meaningless, and `_selection_score()` trusts it. **This should be audited and tested before it lands on `origin/master`.**
- **The quantization *math* itself was not numerically reviewed.** `qat/fake_quant.py` (562 lines) hand-ports libggml's `make_qkx2_quants`, Q2_K/Q3_K/Q6_K, MXFP4 E8M0/E2M1, and IQ4_NL kernels into torch with fixed-point tricks (e.g. Q6_K clamps to `[-31,31]`, dropping ggml's `-32` level) — guarded only by `test_fake_quant.py`, which **skips in CI** (M12). `converters.py`'s BF16 round-to-nearest-even packing and `schemes.py`'s `noise_factor` tables were likewise not verified numerically.
- **`utils/llamacpp.py` (627 lines), the measurement trust boundary, was not read** — it parses `llama-perplexity`/`llama-bench` stdout/stderr into every "measured" number the search trusts.
- **`gguf/reader.py` (338 lines), a from-scratch binary GGUF parser** (`struct.unpack` over file-controlled length/count fields), was not examined for the same untrusted-parser class as M2.
- **`gguf/tensor_groups.py` `TensorGroupClassifier`** — the regex/keyword pass that assigns every tensor to a group (and thus its scheme) — was not reviewed. A silent misclassification of a new arch's expert/router/SSM tensor misquantizes a whole group with no error. This is a correctness linchpin.
- **QAT plumbing beyond `train.py`** (`qat/wrap.py`, `validate.py`, `config.py`, `names.py`, `_ggml_ref.py`) was not reviewed.
- **Docs were not reconciled against code.** CLAUDE.md is partly stale (e.g. it says orchestrator imatrix auto-capture is "deferred to PR4-full," but `ab1d80c` implements exactly that). Any finding that cites CLAUDE.md as ground truth (notably M6) should be re-checked against code.
